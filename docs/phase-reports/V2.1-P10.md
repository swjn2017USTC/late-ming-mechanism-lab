# V2.1-P10 — Replicate Semantics & Pilot Freeze

Status: complete. The determinism question is answered — **`deterministic-replay-by-design`**, not a
wiring blocker — so V2.1-P11's entry condition holds. Run against `docs/exec-plans/V2.1-P10.md`; no
V2.1-P11 work started.

## What the phase was for

P05 ran ten arms at four root seeds each and every arm produced **one** simulation digest with **no**
non-null `rng_draw` row. Two readings were possible and they are not equivalent: a declared draw-free
replay, or a subsystem that should consume its stream and does not. The phase decides which, freezes
what V2 established in the terms its artifacts support, and recomputes the two parameter-registry
defects V2 carried.

The procedure was fixed in `determinism_verdict` before the artifacts were read, and each of its
four steps is measured rather than argued:

| step | what was measured | where it is recorded |
| --- | --- | --- |
| 1. every arm holds one independent process | 10 arms × 4 executions, `distinct digests = 1` per arm | `docs/v2_1/replicate-audit.json` → `arms[].distinct_digests` |
| 2. one forcing path, and it is draw-free | all 40 logs record `observed-historical` / `climate-allocated-observed-v1`, 0 `rng_draw` rows | `arms[].rng_draw_rows`, `determinism.forcing_mode` |
| 3. blocker if a draw-free mode drew | 0 draws anywhere in the 40 logs | `determinism.verdict` |
| 4. which stream the tick path can reach | only `systems/climate.py` names `RngStream.CLIMATE`; the other six streams are named by no tick-path module | `determinism.tick_path_call_sites` |

The premises are quotations the audit re-checks on every run, so a premise that is edited out of the
tree fails the audit instead of surviving it: `AllocatedObservedClimate.shock` "consumes no
randomness", `SyntheticClimate.shock` takes "Two unconditional draws", the overview's climate table
"Replays a sourced series; no randomness", and P03's contract decision "No stochastic household
rule". `tests/unit/test_historical_forcing.py::test_the_shock_interface_consumes_no_randomness`
already covered the interface itself; the audit does not re-test it, it reads what it produced.

The counter-check is what makes step 4 a measurement rather than a claim: **14 stored runs do carry
draws** (2,880 in `outputs/runs/demo-shaanxi-henan-…`, 1,200 each in the twelve `outputs/pilot/v2-p03/`
arms and `outputs/runs/kernel-smoke-…`), every one of them `synthetic` forcing, every one of them
drawing on `climate` alone. The stream is live; the historical core is an instance of a declared
draw-free mode, not a dead stream.

**Conclusion, stated without hedging: the historical core is deterministic replay by design.** Six
streams are declared and seeded, and no system in the tick path consumes them; that is a limitation
of the current model (read "seven streams" as plumbing for common random numbers, not as seven
drawing subsystems), and it is *not* a wiring defect, because no document declares that any of them
must draw on this scenario, and the streams demonstrably draw where a scenario asks for it.

## What the audit found that the phase did not expect — a derived reading is not bit-reproducible

The key-reading column is what surfaced it: `band-merge-negative-control` showed two distinct values
of `band_chain_largest_share_end` across four executions whose simulation digests agree. The logs of
those four executions are **byte-identical** (`sha256 484dba21fb7ac817…` × 4, and the reference arm's
`cfdf4f52f1c24991…` × 4), so the run repeated exactly and the reading did not:

```bash
$ PYTHONHASHSEED=1 uv run python -c "…band_chain_summary(events)['band_chain_largest_share_end'] …×5"
1 ['0.19940185717079706', '0.19940185717079711']
$ PYTHONHASHSEED=2 … 2 ['0.19940185717079711', '0.19940185717079706']
$ PYTHONHASHSEED=3 … 3 ['0.19940185717079706']
```

Five evaluations of one in-memory frame in one process disagree in the last bit, and the effect is
scheduling-dependent rather than certain — the independent review evaluated the reference arm's log
five times and saw one value, which is what a race looks like from outside. The cause is in the
reader, not the run: `analysis/military.py::band_series` computes `largest_band_share` from
`group_by("tick").agg(pl.col("troops").sum())`, a parallel reduction whose association order polars
does not pin, and floating-point addition is not associative (relative spread ~1.2e-16 and 2.8e-16).
This is carried, not repaired: the readers are shared with V1 and V2 documents this phase may not
rewrite, and the fix is a change to a shared analysis module rather than to the audit.

Two consequences the phase had to handle rather than report:

- the audit compares readings at a **declared** 12 significant digits (`READING_SIGNIFICANT_DIGITS`),
  so a last-bit difference is not reported as a behavioural one, and a reading that really moved
  still is (`test_a_reading_that_really_moved_is_not_absorbed_by_the_precision`);
- the audit's *documents* are byte-stable, which they would not be if the run-to-run ULP noise
  decided their contents. Two consecutive generations were diffed: **`BYTE-STABLE`**.

The first draft of the audit did report the divergences per arm, and it was not byte-stable across
generations — the finding is real, but it cannot be a *field* of a generated document. It is a
carried item in the document (`determinism.carried`) with the module and function named, and the
measurement above is its evidence.

A second self-reference was found and fixed the same way: the statement scan read `docs/**/*.md`,
including the audit's own output, so generation *n* quoted generation *n−1*'s line numbers. It was
first narrowed to exclude `docs/v2_1/`, and the independent review then found the same defect one
level up — this phase report quotes the audit's findings verbatim, so with the report in the tree a
regeneration added lines reading `docs/phase-reports/V2.1-P10.md:38: every one of the 40 runs …` and
the committed `replicate-audit.json` stopped reproducing. That is the general form of the mistake: a
scan over "every markdown file" grows as the project writes more, and one of those files is always
about the scan.

The corpus is therefore **declared and closed** — `.omp`, `docs/adr`, `docs/architecture`,
`docs/epistemics`, `docs/mechanisms`, `data/parameters`, `data/protocol` (`STATEMENT_CORPUS`) —
because those are the documents that state how a subsystem is wired. A phase report or an exec plan
records work rather than declaring design, and it may quote this audit. The corpus and the scan's
limits are printed in the document, and a test holds the scan to the corpus
(`test_the_statement_scan_reads_only_the_declared_corpus`).

## The parameter registry

| finding | recomputed | resolution |
| --- | --- | --- |
| `interest_rate_monthly` central `0.005` is below its own range `[0.01, 0.1]` | 1 card | registered carried item |
| range-carrying cards in neither `DECLARED` nor `EXCLUDED` | 37 carry a `range:`, **19** numeric in neither list, **1** text-only (`monthly_allocation_profile`) | registered carried item |
| declared priors the calibration simulator does not rebuild | `pay_tael_per_soldier_month`, `food_shi_per_soldier_month` | registered carried item, and a defect |

Why none of the three was fixed here, in the phase's own words (from the document):

- the **central** may not be moved to fit the range (that is what the plan forbids), the parameter may
  not be excluded (it is a declared prior, so excluding it changes the prior table and the frozen
  posterior's `prior_digest`), and the **card may not be edited** — `data/parameters/*.yaml` is
  covered by `evidence_digest`, which the frozen `outputs/v2/p06/posterior.json` records and which
  recomputes today;
- the **19 cards** need an exclusion *rule* each, and no measurement in this phase produces one;
  inventing nineteen rules would convert an oversight into nineteen fake decisions, which is the
  epistemics this project forbids. Registering the gap with the full enumeration is the honest action;
- the **two dropped priors** are a code defect, not a registry choice: the draw passes `_check`,
  enters `parameter_hash`, and is then dropped by `SandboxSimulator.parameter_sets` because
  `MilitaryParameters` is not in the module's `_DEFAULTS` table. Fixing it changes what the frozen
  posterior means, which is not this phase's to change.

**Discovered by this phase, not carried from a report**: the third finding. V2-P06's and V2-P07's
notes named the first two; nothing had noticed that two of the thirteen declared priors never reach
the model. V2-P06's report also says the prior table is "exactly the parameter cards' ranges, which
is V1's rule kept"; the table is the 13 **declared** cards' ranges, and 19 further range-carrying
cards are in neither list. That sentence is contradicted by the registry and is recorded here rather
than edited there.

### The one existing test that had to change

`tests/unit/test_v2_release.py::test_the_committed_documents_are_what_the_code_produces` failed after
this phase added four source files:

```text
FAILED tests/unit/test_v2_release.py::test_the_committed_documents_are_what_the_code_produces - AssertionError: docs/v2/limitations-v2.md was not produced by this code
  - ackage's 156 sources as `184530a3beac1e7d` and rec
  + ackage's 160 sources as `3ec5182976d46d9e` and rec
1 failed, 68 passed, 2 warnings in 50.47s
```

Only two generated files drift — `docs/v2/limitations-v2.md` and `docs/v2/release-bundle.json` — and
only on that one line, because the Release gate's evidence embeds the code digest and the source
count. The test compared every generated document byte-for-byte against a live regeneration, which
makes it a freeze on the whole `src/` tree: any source edit at all would fail it, for P11 and P12 as
much as for P10. Two things follow, and the first decided the fix:

- regenerating `docs/v2/**` was rejected. Those documents are the record of *which code produced the
  V2 release*; rewriting them under V2.1 code, on a dirty tree, would make the record false — the
  same reasoning P09 used when it regenerated the bundle on a clean tree rather than leave a
  `git_sha` that names a commit without the code it describes.
- the test now masks that one phrase on both sides, asserts it occurs the same number of times on
  both sides, and asserts the committed document's phrase **equals the committed
  `release-bundle.json`**'s `code_files` and `code_digest[:16]`. Everything else is still compared
  byte-for-byte, so a hand-edited card or a status re-pinned after an artifact moved still fails.

The masking is not vacuous, and that was checked rather than assumed: a tampered identity line is
invisible to the masked comparison but is caught by the identity assertion
(`tampered identity differs: True`), and an added or removed occurrence is caught by the count.

## Carried to V2.1-P12 (not fixed here, by design)

1. **The reader reduction order** — `analysis/military.py::band_series` aggregates with a parallel
   `group_by`; derived band readings carry last-bit run-to-run variability. The audit declares its
   comparison precision because of it.
2. **`interest_rate_monthly` central below its range**, and the 19 range-carrying cards in neither
   list, and the text-only range on `monthly_allocation_profile`. Each needs a decision P10 may not
   make alone.
3. **Two declared priors drop before the run** (`MilitaryParameters`). This makes the frozen
   posterior's 13-parameter draw space effectively 11-parameter, which belongs in the calibration
   card P12 writes.
4. **`docs/phase-reports/V2-P06.md`'s prediction gate wording** and **its prior-table sentence** are
   contradicted by the artifacts; P12's documentation should carry the corrected statements.
